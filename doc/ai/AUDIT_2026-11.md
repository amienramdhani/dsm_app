## Bagian 6 — Rahasia / kredensial yang ter-commit

Yang dipindai: semua file yang dilacak git di `dev` (411 file). Riwayat commit lama **tidak** dipindai (clone dangkal), jadi rahasia yang pernah ter-commit lalu dihapus tidak akan kelihatan di sini.

### S-1 · `config.php` ter-commit dan berisi nilai PEPPER — KRITIS

- **Lokasi:** `config.php:17` (`define('DSM_PEPPER', '…')`), plus `config.php:20-24` (host/nama DB/user).
- **Fakta:** `.gitignore` baris 6 mencantumkan `config.php`, tapi file ini **sudah telanjur dilacak git**, jadi `.gitignore` tidak berpengaruh. Isinya bukan sekadar "memuat `config.local.php`" seperti yang tertulis di aturan kerja; nilai PEPPER ditulis langsung di file. Tidak ada kode yang memuat `config.local.php` sama sekali (dicari di seluruh repo: nol hasil selain satu komentar di `lib/api_exec.php:134`).
- **Kenapa berbahaya:** PEPPER dipakai untuk 4 hal sekaligus:
  - kunci hash PIN (`lib/auth.php:10-12`),
  - kunci enkripsi rahasia Authenticator/2FA (`lib/totp.php:83-84`),
  - kunci enkripsi PIN sementara yang bisa dilihat Admin (`lib/auth.php:53-54`),
  - hash token sesi (`hash_()` dipakai di `SESSION_…`).
- **Skenario gagal:** siapa pun yang bisa membaca repo (kolaborator, token yang bocor, repo final `amienramdhani/dsm_app` kalau file ini ikut ditransfer) + dapat salinan tabel `_Auth` (misal dari file backup) bisa menebak semua PIN: PIN cuma 4 digit = 10.000 kemungkinan per akun, selesai dalam hitungan detik. Rahasia 2FA yang tersimpan juga bisa dibuka.
- **Bentrok dengan dokumen:** `doc/ai/HANDOFF.md` (bagian Current Status) menulis "Local secrets are separated from tracked configuration". Untuk `config.php` di `dev` itu tidak benar.
- **Yang gue TIDAK tahu:** apakah nilai di repo ini sama dengan yang dipakai server produksi. Kalau server memakai nilai lain, risikonya turun jadi SEDANG (tetap harus dibereskan).
- **Usulan (butuh persetujuan, belum dikerjakan):**
  1. Cek dulu: nilai PEPPER di server sama atau tidak dengan yang di repo.
  2. Keluarkan `config.php` dari git (`git rm --cached`), ganti dengan `config.php` yang hanya memuat `config.local.php` + sediakan contoh tanpa nilai asli.
  3. Kalau nilainya sama dengan produksi: PEPPER harus diganti. Dampaknya besar (semua PIN & 2FA harus dibuat ulang), jadi perlu dijadwalkan, bukan dadakan.
  4. Menghapus dari riwayat git itu langkah terpisah (rewrite history) — perlu keputusan user.

### S-2 · 220 file cache jawaban API berisi data asli ikut ter-commit (±230 MB) — KRITIS

- **Lokasi:** `storage/cache/*.json` (220 file dilacak git). `.gitignore` hanya mengecualikan `storage/files/`, bukan `storage/cache/`.
- **Fakta:** ini hasil `dsm_cache_put_()` (`lib/rescache.php:35`), yaitu salinan jawaban API apa adanya. 205 dari 220 file memuat field `nik`/`nama`. Contoh isi: daftar orang dengan NIK, nama, jabatan, region, qty, **omzet rupiah**, target.
- **Skenario gagal:**
  - Semua yang punya akses repo bisa baca angka penjualan & omzet per orang tanpa login DSM.
  - NIK = ID login. Digabung dengan S-1, ini daftar lengkap akun yang bisa dicoba.
  - Kalau repo ini di-deploy dengan `git pull`, server ikut memuat cache basi dari laptop (kunci cache memuat revisi data, jadi kemungkinan besar tidak terpakai, tapi tetap sampah 230 MB).
- **Catatan web:** akses lewat browser ke `storage/` ditolak `storage/.htaccess` — **hanya berlaku di Apache**. Kalau server memakai Nginx, `.htaccess` tidak dibaca sama sekali (berlaku juga untuk `lib/`, `tools/`, `klaim/storage/`). Perlu dicek jenis web server produksi.
- **Usulan:** tambah `storage/cache/` ke `.gitignore`, `git rm -r --cached storage/cache`. Soal riwayat git sama seperti S-1.
- **Catatan riwayat:** `doc/ai/CHANGELOG_AI.md:784-785` mencatat masalah ini **pernah dibereskan** ("`storage/cache/` dan `*.zip` masuk `.gitignore`, file cache dilepas dari index"). Di `dev` sekarang `.gitignore` tidak memuat baris itu dan 220 file kembali terlacak — perbaikan lama hilang (kemungkinan tertimpa saat ada commit/penggabungan berikutnya). Perlu dicari kapan baris itu hilang supaya tidak terulang.

## Bagian 1 — Hak akses API

### Cara memeriksa

  - `adminGuard_()` → ADMIN **atau** SUPER ADMIN (`lib/publish.php:220-223`).
  - Batas wilayah Admin biasa = `canManageUser_()` (`lib/publish.php:225`), `dbaCanManageNik_()`, `mcCanEdit_()`, `contactCanReview_()` — semuanya berbasis `adminRegions`.

### Hasil utama DSM (`api.php`)

### A-1 · Klaim: daftar klaim & petty cash bisa dibuka siapa saja yang punya akses Klaim — TINGGI

- **Lokasi:** `klaim/lib/query.php:49-57` (`claim_list`, view `queue` / `ba` / `proses` / `selesai`), `klaim/lib/query.php:167-175` (`pc_list`, view `queue` / `ft` / `monitor` / `proses`), dipanggil langsung dari `klaim/api.php:64` dan `klaim/api.php:86` tanpa `need_role`.
- **Masalah:** pembatasan di daftar hanya dipasang **kalau** user punya peran (Admin → region, Audit/FM/FT → badan usaha). Kalau user tidak punya peran sama sekali (Pemohon biasa: Sales/ASM), tidak ada satu pun pembatas yang dipasang. Parameter `stage` juga diterima apa adanya tanpa dicek user punya peran itu atau tidak (`query.php:49`, `query.php:170`).
- **Skenario gagal:** seorang Sales yang hanya boleh mengajukan klaim mengirim request `a=claim_list&view=selesai` (atau `view=proses`, atau `view=queue&stage=FT`) → mendapat daftar klaim **seluruh perusahaan**: nomor, nama pemohon, jabatan, region, badan usaha, kategori, nominal, status (`row_out`, `query.php:11-19`). Dengan `a=pc_list&view=monitor` dapat semua petty cash yang sedang berjalan, lengkap dengan rencana, nota, dan nominal (`pc_out` mengembalikan seluruh kolom, `query.php:155-165`).
- **Yang tetap aman:** membuka detail satu klaim (`claim_detail`), unduh berkas, PDF, dan **semua aksi approve/tolak/transfer** tetap dicek (`can_view`, `stage_owner_ok` di `klaim/lib/claims.php:472-478`, `pc_stage_ok`). Jadi ini bocor baca-daftar, bukan bisa menyetujui.
- **Usulan:** di `claim_list` dan `pc_list`, untuk view selain `mine`: wajib punya salah satu peran pengelola; `stage` harus peran yang memang dipegang user; kalau tidak punya peran → paksa `claimant_id = saya`. Ini pas dikerjakan bareng bagian Klaim Mode Demo karena fungsi yang sama juga harus disaring untuk data demo.

### A-2 · Klaim: daftar & monitoring Admin hanya melihat `region`, mengabaikan "wilayah tugas" (`areas`) — TINGGI

- **Lokasi:** `klaim/lib/query.php:38-42` (`$scopeSql`), `klaim/lib/query.php:170,173` (`pc_list`), `klaim/lib/report.php:12` (`monitor_budget`), `klaim/api.php:111-113` dan `:169-171` (`people_admin`, `contact_template` — dua ini sudah benar memakai `area_list`).
- **Fakta:** wewenang Admin/RGM yang sebenarnya dihitung `covers_region()` (`klaim/lib/core.php:25-29`): daftar wilayah (`areas`) menang, `region` tunggal hanya cadangan. Tapi daftar klaim, antrean petty cash, dan monitoring budget menyaring pakai `$u['region']` saja.
- **Skenario gagal (dua arah):**
  1. Admin yang diatur lewat `areas` = "Cirebon, Tegal" dan `region` kosong → saringan tidak terpasang → di daftar/antrean/monitoring/export ia melihat **semua region**. (Aksi approve tetap ditolak untuk region lain, tapi datanya terlihat dan ikut ter-export.)
  2. Admin dengan `region` = Cirebon dan `areas` = "Cirebon, Tegal" → antreannya hanya menampilkan Cirebon. Klaim Tegal **tidak muncul di antrean siapa pun** padahal hanya dia yang berwenang → klaim nyangkut.
- **Usulan:** satu fungsi pembuat saringan SQL yang memakai aturan yang sama dengan `covers_region()`, dipakai di `claim_list`, `pc_list`, `monitor_budget`, `counts`.
- **Terkait:** Admin/RGM yang `areas` dan `region`-nya dua-duanya kosong dianggap **memegang semua region** (`core.php:126`, memang ditulis sengaja di komentar `core.php:24`). Layar Super Admin sudah punya pengecekannya (`area_check`, `klaim/api.php:251-254`). PERLU KONFIRMASI apakah "kosong = semua" masih diinginkan; lebih aman "kosong = tidak ada".

### A-3 · Klaim: saat "Mode tes" menyala, Super Admin bisa menyetujui & mengubah data ASLI atas nama siapa pun — TINGGI (masukan wajib bagian Klaim Mode Demo)

- **Lokasi:** `klaim/lib/core.php:61` (`sa_free`), dipakai sebagai jalan pintas di 12 tempat di `klaim/lib/claims.php` + `klaim/lib/pc.php` (contoh `claims.php:473`, `pc.php:12`), `klaim/api.php:11-12`, dan `klaim/api.php:28-29` (larangan menulis saat "masuk sebagai" **hanya berlaku kalau Mode tes mati**), `klaim/api.php:33-38` (`switch_user` menerima **user mana pun**, bukan cuma akun uji).
- **Skenario gagal:** Mode tes dinyalakan di server asli untuk demo → selama menyala, Super Admin (a) lolos semua cek tahap: bisa approve/tolak/transfer klaim **asli** di tahap mana pun (hanya ditandai `[MODE TES]` di riwayat, `claims.php:496`), (b) bisa "masuk sebagai" **orang asli** lalu mengajukan/menyetujui atas nama orang itu, (c) lolos larangan "klaim sendiri".
- **Kenapa penting untuk Klaim Mode Demo:** brief minta "data demo TIDAK BOLEH memotong budget asli". Selama `sa_free()` berlaku untuk semua data, Mode Demo yang baru tetap bisa menyentuh data asli.
- **Usulan (untuk dibahas sebelum koding Klaim, belum dikerjakan):** kekuatan khusus Mode Demo hanya berlaku pada **akun & data demo** — `switch_user` hanya ke akun `UJI-*`; `sa_free()` hanya bernilai benar bila klaim/petty cash-nya bertanda demo; menulis atas nama orang asli tetap dilarang walau Mode Demo menyala.

#### D-5 · "Dealer Aktif" KPI menghitung pasangan dealer-brand, status AKTIF menghitung dealer — TINGGI untuk Paket Status Dealer · PERLU KEPUTUSAN

- **Lokasi:** `lib/core.php:161-172` — kunci hitung DA = `customer + brand`, juga saat brand = ALL.
- **Contoh angka:**
  - Dealer beli 1 Infinix + 1 Tecno → status total **AKTIF** (2 unit), tapi DA KPI = **0** (tidak ada brand yang mencapai 2).
  - Dealer beli 2 Infinix + 2 Tecno → status total AKTIF = 1 dealer, tapi DA KPI (ALL) = **2**.
- **Bentrok dengan brief:** "Jumlah *sudah order bulan ini* harus sama dengan angka DA di KPI" dan kartu "SUDAH ORDER <BLN> = DA KPI". Dengan definisi sekarang, angka DA KPI adalah jumlah **pasangan dealer-brand**, dan nilainya juga bergantung indikator (min unit per brand bisa beda, ACC per promotor, wajib tipe tertentu). - **Rekomendasi gue:** (a) untuk toggle **PER BRAND** (jumlah dealer yang memenuhi DA brand itu = persis angka DA KPI brand itu), dan untuk toggle **TOTAL** tampilkan jumlah dealer dengan keterangan ⓘ "beda dengan DA KPI karena KPI menghitung per brand". Jangan memaksa satu angka untuk dua definisi.

#### D-6 · KPI "Dealer Idle" ≠ status IDLE — RENDAH (sudah diketahui, dicatat supaya tidak tertukar)

Arahnya berlawanan. ## Bagian 4 — Bug logika: KPI / achievement, DOS, transfer dealer, kredit tetap ke penjual

Semua temuan di bagian ini berasal dari **membaca kode**, belum direproduksi dengan data asli. Yang perlu dites dulu sebelum diperbaiki ditandai "PERLU DITES".

Fakta dasar yang dipakai beberapa temuan: pemilik efektif tiap transaksi **dihitung ulang setiap publish** untuk **semua bulan** (`lib/publish.php:184-185` → `effectiveRows_`, `lib/tx_effective.php:92`). "Kunci periode" hanya menolak aksi tulis tertentu (`assertPeriodOpen_`, `lib/publish.php:235-238`); angka bulan yang dikunci **tidak dibekukan**. Jadi apa pun yang mengubah aturan kepemilikan dengan tanggal mundur akan mengubah angka bulan lama pada publish berikutnya.

### B-1 · Kredit tetap ke penjual: menambah aturan lagi untuk orang yang sama MENGHIDUPKAN kembali bulan yang sudah dicabut — TINGGI · PERLU DITES

- **Lokasi:** `lib/keep_seller.php:110` (mengambil semua aturan `active = 1` untuk subjek yang sama), `:121-123` (memotong aturan lama), `:142-146` (cabut).
- **Akar masalah:** "Cabut" tidak menonaktifkan aturan; ia hanya mengisi `period_to` dan aturan tetap `active = 1` (`:146`). Saat aturan baru disimpan, **semua** aturan lama yang mulainya lebih awal diberi `period_to = <periode baru>` (`:122`) — termasuk aturan yang sebenarnya **sudah berakhir** lebih dulu.
- **Skenario gagal:**
  1. Oktober: Super Admin membuat kredit tetap untuk RGM "Budi" mulai `2026-10`.
  2. November: dicabut, berakhir sebelum `2026-11` → aturan = Okt saja.
  3. Januari: dibuat lagi untuk Budi mulai `2027-01`.
  4. Baris `:122` mengubah aturan lama menjadi berakhir sebelum `2027-01` → aturan lama sekarang mencakup **Okt, Nov, Des**.
  5. Publish berikutnya: transaksi Budi bulan **November dan Desember** (yang tadinya sudah dialihkan ke pemilik dealer) kembali menjadi milik Budi. KPI/achievement pemilik dealer di Nov–Des turun, walau dua bulan itu mungkin sudah dikunci dan insentifnya sudah dibayar.
- **Hal yang sama di "Cabut":** mencabut aturan yang sudah punya tanggal akhir dengan periode yang lebih jauh akan **memperpanjang**-nya (`:142` hanya membandingkan dengan `period_from`). Dan bila publish gagal, pemulihannya mengosongkan `period_to` (`:144`) → aturan jadi berlaku selamanya, bukan kembali ke nilai sebelumnya.
- **Usulan:** saat menyimpan, hanya potong aturan lama yang `period_to` kosong atau lebih besar dari periode baru; saat mencabut, tolak bila `period_to` sudah terisi dan lebih kecil; pemulihan mengembalikan nilai `period_to` lama.

### B-2 · Kunci periode tidak melindungi dari transfer dealer bertanggal mundur — TINGGI

- **Lokasi:** `lib/dealer_brand.php:78-102` (`dbaSet_`), `lib/bulk.php:475-493` (`transferRows_`, hanya menolak tanggal **masa depan** di `:486`), `lib/api_dealer_transfer_direct.php:203`, `lib/api_portfolio.php:190` (Alihkan Portofolio). **Nol** pemanggilan `assertPeriodOpen_` di empat file itu. Pembanding: Koreksi Transaksi **sudah** mengeceknya (`lib/api_txcorr.php:141`, `:182`, `:230`).
- **Skenario gagal:** Oktober sudah dikunci dan KPI-nya sudah dipakai menghitung insentif. Di pertengahan November, Admin (cukup Admin wilayah) melakukan Transfer Dealer dengan `EFFECTIVE_DATE = 2026-10-01`. Tidak ada penolakan. Pada publish berikutnya seluruh ST Oktober dealer-brand itu pindah dari Sales lama ke Sales baru → KPI Oktober dua orang berubah diam-diam. Foto "Riwayat Pemilik" yang diambil saat kunci (`lib/api_import.php:340-343`) tetap menunjukkan pemilik lama, jadi layar Riwayat dan angka KPI tidak cocok lagi.
- **Usulan:** `dbaSet_` (satu pintu untuk semua jalur) menolak tanggal efektif yang jatuh di bulan terkunci, dengan pesan yang sama seperti Koreksi Transaksi. Super Admin tetap bisa membuka kunci dengan alasan.

### B-3 · Transfer per brand baru terasa di KPI setelah publish berikutnya; menu Transaksi langsung berubah — SEDANG · PERLU DITES

- **Lokasi:** `lib/bulk.php:533` — publish hanya dijalankan bila ada baris `BRAND = ALL`. Transfer brand tertentu (`lib/bulk.php:528`), "PIC Dealer Brand" manual (`lib/dealer_brand.php:137-139`), dan Transfer Dealer langsung hanya menulis tabel penugasan (`dbaWrite_`, `lib/dealer_brand.php:72-75`) tanpa publish dan tanpa menaikkan revisi data.
- **Akibat:** Beranda/KPI/Peringkat (dibaca dari ringkasan hasil publish) masih memakai pemilik lama sampai ada upload ST/SO atau publish lain. Menu Transaksi, export RAW, dan antrean koreksi (memakai `txEffRaw_`, dihitung saat dibaca: `lib/api_menu.php:38`, `lib/api_export2.php:627`) sudah memakai pemilik baru.
- **Skenario:** Admin mentransfer brand Infinix dealer X ke Sales B jam 10.00. Sales B membuka Transaksi: transaksi Infinix dealer X sudah atas namanya. Membuka KPI: qty-nya belum bertambah. Baru sama setelah upload harian berikutnya. Karena upload dilakukan harian, selisihnya biasanya hilang dalam sehari — tapi di akhir bulan/saat penutupan ini bisa menyesatkan.
- **Usulan:** setelah transfer per brand, jalankan publish yang sama seperti `BRAND = ALL` (atau tampilkan pemberitahuan "berlaku di KPI setelah data diperbarui").

### B-4 · Kredit tetap berbasis ROLE memakai jabatan orang SAAT INI, berlaku surut — SEDANG

- **Lokasi:** `lib/keep_seller.php:48-57` — jabatan diambil dari struktur sekarang, bukan struktur pada bulan transaksi.
- **Skenario:** aturan awal "HEAD OF SALES = kredit tetap" berlaku sejak Oktober. Seorang RGM dipromosikan menjadi Head of Sales di Desember. Pada publish berikutnya, transaksi yang ia input sendiri di **Oktober–November** (waktu masih RGM, dan saat itu dialihkan ke pemilik dealer) berubah menjadi kredit tetap atas namanya. Sebaliknya juga berlaku saat turun jabatan.
- **Usulan:** saat seseorang berganti jabatan masuk/keluar role yang punya aturan, buat aturan PERSON eksplisit dengan periode; atau baca jabatan dari foto struktur bulanan (sudah disimpan saat kunci periode).

### B-5 · Achievement atasan menggelembung bila sebagian bawahannya belum punya target — SEDANG · PERLU KONFIRMASI

- **Lokasi:** `lib/core.php:249-259` (`target()` — menjumlah target **hanya** dari orang yang punya baris target, sisanya masuk `missing`), `lib/core.php:330` (`kpi()` — selama total target > 0, achievement dihitung; daftar `missing` tidak dipakai).
- **Skenario:** ASM punya 5 Sales. 4 Sales diberi target ST Infinix masing-masing 100 (total 400); Sales kelima targetnya lupa diisi. Aktual tim = penjualan **kelima** Sales, misal 480. Achievement ASM = 480 / 400 = **120%**, padahal kalau target Sales kelima (100) terisi hasilnya 96%.
- **Catatan:** untuk perorangan tidak masalah (target kosong = "TIDAK DIWAJIBKAN"). Masalahnya hanya di gabungan tim/region. Kartu Beranda sudah menampilkan daftar `missing`, tapi skor KPI tidak menandainya sebagai sementara.
- **Usulan:** bila `missing` tidak kosong pada level tim, beri status "SEMENTARA · target belum lengkap" (tanpa mengubah rumus), atau keluarkan aktual orang yang tidak bertarget dari pembilang. Ini mengubah angka KPI → **wajib keputusan user**.

### B-6 · DOS: barang dengan sell out bersih NEGATIF diberi status "MENIPIS" — RENDAH

- **Lokasi:** `lib/stock.php:156-157`.
- **Akar:** bila sell out 30 hari bernilai minus (retur lebih besar dari jual), rata-rata harian ≤ 0 → DOS = kosong. Pemilihan status lalu membandingkan "kosong < batas minimum", yang di PHP bernilai benar → **MENIPIS**.
- **Skenario:** dealer punya stok 20 unit tipe A, bulan ini hanya ada retur SO 2 unit. Tampil sebagai "MENIPIS" (seolah stok hampir habis dan perlu dikirim), padahal seharusnya "BELUM BERGERAK" atau "PERLU CEK DATA". Ikut masuk hitungan jumlah "menipis" di ringkasan dan export DOS (`lib/api_export2.php:433`).
- **Usulan:** perlakukan sell out ≤ 0 sama dengan 0 pada pemilihan status.

### B-7 · Status di Detail Dealer salah untuk dealer IDLE/PASIF — TINGGI (lihat D-1 di Bagian 2)

### B-8 · Hal yang diperiksa dan TIDAK ditemukan masalah

- Rumus skor KPI: bobot per kelompok divalidasi tepat 100 (`lib/core.php:537`, `lib/publish.php:375`, `lib/api_kpikhusus.php:202`), skor akhir = rata-rata kelompok, batas skor (`cap`) diterapkan. Konsisten antara KPI biasa, KPI RGM, dan keterangan di layar.

- DOS mengikuti pemilik/lokasi dealer (bukan penjual), sesuai aturan tetap.
